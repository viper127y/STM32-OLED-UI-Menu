 [1] FreeRTOS 内核文件怎么分工? (核心必懂 3 个)
----------------------------------------------------------------
 £★ 说明:
 tasks.c : 任务调度器, FreeRTOS 的心脏, 管任务创建/切换/优先级调度
 queue.c : 队列 + 信号量 + 互斥量, 任务间传数据和同步全靠它 (信号量就是特殊队列)
 list.c  : 链表, 调度器的底层数据结构, 不用直接碰

 [2] FreeRTOS 内核文件怎么分工? (移植相关 2 个)
----------------------------------------------------------------
 £★ 说明:
 port.c   : 移植层, 跟 CPU 架构相关 (F1 是 Cortex-M3 版), 上下文切换/PendSV 在这
 heap_4.c : 内存管理, xTaskCreate 的内存从这来, 支持申请+释放+碎片合并

 [3] FreeRTOS 内核文件怎么分工? (按需选配 5 个)
----------------------------------------------------------------
 £★ 说明:
 timers.c       : 软件定时器, 基于 Tick 的回调

 [5] CubeMX FreeRTOS Config parameters 里哪些配置常用?
----------------------------------------------------------------
 £★ 说明:
 90% 保持默认, 真正常动的就几个:
 TOTAL_HEAP_SIZE   : 最常改! 任务/队列建不起来第一反应就是加大它
 TICK_RATE_HZ      : 1000 即 1ms 一个 tick, vTaskDelay(1) = 1ms, 别乱动
 MINIMAL_STACK_SIZE: 默认栈大小, 128 Words = 512 字节, F1 RAM 紧张够用就好
 MAX_PRIORITIES    : 优先级上限, 16~32 就够, 越小越省内存

 理解就行:
 USE_PREEMPTION = Enabled : 抢占调度, 必开
 CPU_CLOCK_HZ             : 自动跟主频走
 USE_MUTEXES / USE_COUNTING_SEMAPHORES : 让互斥量/计数信号量可用, 默认开
 IDLE_SHOULD_YIELD        : 空闲任务让出 CPU, 保持默认

 排错救命 (Advanced settings 页):
 CHECK_FOR_STACK_OVERFLOW : 栈溢出检测, 调试玄学 HardFault 时开成 2
 configASSERT             : 参数断言, 开发期开着抓 API 传参错误

 口诀:
 任务建不起来   -> 加 TOTAL_HEAP_SIZE
 跑飞/HardFault -> 开栈溢出检测
 vTaskDelay 多久 -> 看 TICK_RATE_HZ
 其他全默认

 [6] 程序是怎么跑到我的任务函数里的? (CMSIS-OS2 工作流)
----------------------------------------------------------------
 £★ 说明:
 调用链:
 main()                              [main.c L66]
  -> HAL_Init / SystemClock_Config / MX_GPIO_Init
  -> MX_FREERTOS_Init()              [freertos.c L72]  只登记任务, 没运行!
     -> osThreadNew(vUiTask, ...)    [freertos.c L95]  UiTask 在这里被创建
  -> osKernelStart()                 [main.c L100]     启动调度器, main 回不来了
     -> 调度器挑最高优先级就绪任务
        -> 上下文切换 -> 跳进 vUiTask() while(1)

 核心: 创建 != 运行
 osThreadNew 只是 "报名": 从 heap_4 分配栈和 TCB, 挂到就绪列表排队
 osKernelStart 才是 "开赛": 配好 SysTick (心跳) + PendSV (切换), 跳进最高优先级任务
 之后 CPU 在各任务 while(1) 之间来回跳, main 停在 osKernelStart 永远往下不走

 细节: freertos.c 里有 __weak void vUiTask() 空壳,
 真正实现在 User/Task/Ui_Task.c, weak 作用是链接器优先用你自己写的同名函数,
 CubeMX 重新生成代码也不会覆盖你的任务

 [7] osKernelInitialize() 是干嘛的?
----------------------------------------------------------------
 £★ 说明:
 一句话: 给 RTOS 内核 "开门营业", 把内核从 Inactive 切到 Ready 状态,
 之后才允许调 osThreadNew 等创建 API, 否则直接返回错误

 实际很轻: cmsis_os2.c 里核心就是 KernelState = osKernelReady 这一下
 重活不在这: SysTick 心跳 / PendSV 切换 / 真正启动调度器都是 osKernelStart 干的

 CMSIS-OS2 三步生命周期 (对应 main.c L94~L98):
 osKernelInitialize() : 1. 开门   允许创建 RTOS 对象
 MX_FREERTOS_Init()   : 2. 报名   创建任务/队列 (还没跑)
 osKernelStart()      : 3. 发令枪 调度器开跑, main 退役

 好处: 对象都在调度器启动前建好, 系统一开跑就是完整状态

 坑:
 顺序不能乱 -> osThreadNew 放在 Initialize 之前会创建失败 (返回 NULL)
 别漏掉     -> 原生 xTaskCreate 不调它也能跑, 但走 osXXX API 必须先 Initialize

 口诀: Initialize 开门, 创建任务排队, Start 开赛

 [8] #if defined(XXX) 这种写法是什么? 为什么要这样写?
----------------------------------------------------------------
 £★ 说明:
 这叫条件编译: 编译器在编译前先 "裁剪" 代码,
 宏没定义 -> 这段代码当不存在, 连一行指令都不生成 (不是运行时跳过)
 例: 工程用 heap_4, USE_FreeRTOS_HEAP_5 没定义,
     vPortDefineHeapRegions 就完全没进 .o 文件
 这就是笔记 [4] 说的 "宏一关就不参与编译" 的底层机制

 #if (编译时) vs if (运行时) 对比:
 判断时机 : 预处理阶段, 编译之前 | 芯片运行时
 代码体积 : 没定义就完全不存在   | 函数照常编译进去
 依赖对象 : 必须是宏 (编译期常量) | 必须是变量

 为什么必须用 #if 的两个原因:
 1. 像 EvrFreeRTOSSetup 这种函数, 只有开了 trace 功能才存在
    (函数定义本身也被条件编译包着), 用运行时 if 去调,
    没开 trace 的工程直接链接报错 undefined symbol
 2. F1 只有 20K RAM, 没用的功能一行都不能浪费,
    条件编译让裁剪发生在编译期, flash/RAM 一点不吃

 记住场景:
 配置不同 -> 编译不同 (芯片型号/内存方案 heap_1~5/可选功能) -> #if defined(XXX)
 数据不同 -> 逻辑不同 (传入参数/传感器读数)                 -> 普通 if

 条件编译家族: 头文件 #ifndef XXX_H 防重复包含, USER CODE 保护块, 全是这家的

 口诀: #if 是编译期开关, 按配置裁出不同固件; if 是运行时判断, 同一份固件走不同的路
